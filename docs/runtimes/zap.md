# OWASP ZAP

Cyberful ships headless OWASP ZAP 2.17.0, Firefox ESR/Xvfb, its pinned add-ons, and a bundled stdio bridge inside the unified cyberful-os image. Live-target engagements run that image as a dedicated ZAP container, isolated from the more privileged core cyberful-os/Ghidra container; phase gateways open fresh bridge processes with `docker exec` in the ZAP container.

The builtin `operate-zap` skill is the agent-facing operational contract for this runtime. It centralizes selective history reads, credential-preserving replay, exact raw-request handling, evidence interpretation, and the host-owned passive checkpoint contract. The active phase persona still owns when ZAP work is required and what traffic the mission authorizes; the skill does not expand engagement authority.

Bridge-owned tool definitions live in one static catalog and are merged with the official upstream ZAP tools at startup without renaming either surface. The bridge exposes the complete discovered ZAP API catalog and does not enforce an origin allowlist, redirect policy, or a separate operation denylist. This is deliberate: the active workflow mission and agent instructions own engagement scope, while ZAP remains a fully capable analysis runtime.

Call `zap_api_catalog` before a generic `zap_api_call`. The catalog reflects the installed ZAP version and includes known required and optional parameters. The bridge validates operation names and these parameter contracts locally, so missing operations, missing parameters, and missing resources return distinct structured errors with a bounded list of alternatives instead of an opaque HTTP 400. In particular, `script:action:load` requires `scriptName`, `scriptType`, `scriptEngine`, and `fileName`; `script:view:globalCustomVar` requires `varKey`.

The browser is proxied through ZAP by default. Only internal port 8080 is published as `127.0.0.1:<random-port>`; MCP and service control stay inside the container. Browser trust is scoped to the engagement CA public-key pin. cyberful-os clients receive a read-only engagement bundle containing the system roots plus that same attested public CA. Bridge and API keys remain host-owned private environment values.

```dotenv
CYBER_ZAP_ENABLED=1
CYBER_BROWSER_THROUGH_ZAP=1
```

`CYBER_ZAP_ENABLED=0` is accepted only for workflows that do not require live-target interception. Pentest and Bug Bounty Program always require a healthy ZAP runtime and never start a phase on the direct browser route. `CYBER_BROWSER_THROUGH_ZAP=0` keeps scanning available without browser proxying only outside that fail-closed live-target contract. Ordinary environment settings cannot grant target access: live-target workflows remain bounded by `MISSION.md`, while Code Audit remains offline and never starts ZAP.

Build with `make runtime-build`, then exercise the existing image with `make test-zap`. ZAP's named session, CA, keys, and runtime state persist under an opaque session-owned child of the owner-only `raw/zap/runtime/` workarea subtree across a controlled service or container recovery. This prevents two concurrent session owners of the same workarea from sharing a ZAP home or private key. Reports written under `/zap/wrk` persist in the same mounted workarea.

ZAP history stores response bodies in a bounded HSQLDB `VARBINARY` column. Cyberful sets `database.response.bodysize` explicitly from `CYBER_ZAP_MAX_HISTORY_RESPONSE_BYTES`, defaulting to 1 GiB so large browser acquisitions remain persistable instead of failing at ZAP's 16 MiB upstream default. Startup accepts only decimal values from 16 MiB through 2,147,483,647 bytes. This history copy is distinct from the content-addressed artifact produced by the approved download path; operators may lower or raise the bound within that range according to engagement storage needs.

Code Audit creates only the core container with `--network none` and never starts ZAP. A ZAP process that dies is not automatically restarted. Before every live-target phase attempt the host checks supervisor state, the ZAP API, the MCP `zap_version` call, session generation, the public CA's SPKI and certificate fingerprint, the cyberful-os bundle digest and chain, the engagement traffic-policy rules, and an end-to-end TLS client canary. The host starts one ephemeral HTTPS origin only on the engagement's private Docker network, exposes no host port, and sends every supported client present in the core image through the real ZAP proxy: curl/OpenSSL, Git HTTPS, Python Requests/pip, Node, and Ruby/Bundler. The canary serves only generated local test material, is removed before the AgentRun starts, and never contacts the Internet or target. One client failure blocks the attempt as retryable `required_upstream_unavailable`, making proxy routing, CA propagation, and client-specific trust failures distinguishable from target WAF or browser policy. The private root CA and key are created with owner-only permissions in the session-owned child under `raw/zap/runtime/`, visible to ZAP but masked from the core. `root-ca-public.pem`, `ca-bundle.pem`, and a public-metadata-only `attestation.json` are written atomically in the corresponding session-owned child under `raw/zap/trust/`, which becomes that core's read-only trust mount. The persisted fingerprint, SPKI, and bundle digest anchor continuity across a complete host control-plane restart; malformed, symlinked, or mismatched persisted material fails closed instead of being silently replaced. An initial startup-attestation failure retains the dedicated container for this preflight instead of removing it or enabling direct traffic. An unhealthy service first receives one explicit session-preserving restart; both CA identifiers must remain unchanged. If continuity cannot be attested, the host may advance to a visibly new session generation and records any authorized rotation and durable-anchor replacement only after the new bundle is verified. Failure after bounded recovery is classified as retryable `required_upstream_unavailable` before the worker starts.

ZAP is deliberately absent from `runtime_status`: that gateway tool may reconnect only phase-owned browser and Ghidra MCP bridges, while ZAP recovery belongs to the host lifecycle that preserves and re-attests the named session, CA, proxy trust, and canary results. Calling `runtime_status` with `runtime=zap` returns the non-retryable `MCP_RUNTIME_UNKNOWN` contract and the currently available managed labels; it does not imply that the ZAP service is unhealthy.

## Engagement traffic policy

Brief writes the non-secret `raw/policy/engagement.json` in two stages. `engagement_policy configure` runs after policy acquisition and before any numbered target-profile status check or target navigation. It persists authorized HTTP host patterns, an optional aggregate HTTP RPS limit, and mandatory public request headers with their exact host scopes only after ZAP accepts and attests those controls. `engagement_policy finalize` runs after account preflight, adds the non-secret profile readiness projection, reattests the controls, and marks the policy final; Brief handoff rejects a missing, traffic-only, or inherited final policy that was not updated in the current phase.

When the policy contains a numeric aggregate HTTP RPS limit, Cyberful installs one Network add-on rule with `groupBy=rule` across the authorized host patterns. Browser profiles, ZAP replays, and proxy-aware cyberful-os clients therefore share one counter rather than receiving separate per-host budgets. When the policy mandates a non-secret public request header, Cyberful installs one Replacer `REQ_HEADER` rule for that name and an HTTP(S) URL regex derived only from the declared host scope. The header is added after the browser's CORS decision; browser-global header mutation is unavailable because it would add the name to cross-origin preflights and can break otherwise healthy applications. Values for credentials, cookies, authorization, API keys, tokens, passwords, secrets, and session-variable references are rejected at the policy boundary instead of being stored or returned through this mechanism.

The persistent ZAP runtime retains these rules across phase handoffs. Every preflight removes prior Cyberful-owned rules by their unique descriptions, installs the current controls, and verifies the exact expected registry entries. The Network API registry is read from its advertised `getRateLimitRules` response field; the legacy `rateLimitRules` field remains accepted for compatible older runtimes. The Replacer registry must return its advertised `rules` array, and each installed entry must match its enabled state, `REQ_HEADER` type, literal header name and replacement, and host URL regex. A missing numeric limit or required header set returns the explicit successful state `not_required`; it is not a failed ZAP configuration. ZAP disabled, unavailable, or unable to accept and attest the current policy is a hard upstream failure for every live-target phase; direct browser fallback is not allowed.

ZAP lifecycle evidence is append-only in `raw/operations/zap-runtime.jsonl`. It records phase, attempt, supervisor status, exit code or signal, restart count, session generation, continuity resets, non-secret CA fingerprint/SPKI and bundle digests, authorized rotation, traffic-policy, rate-limit, and required-header attestation, dedicated-container cgroup `memory.events` deltas, and `tls_client_canary` results. Canary diagnostics record each present client, expected bundle/SPKI, outcome, exit class, and sanitized cause; they never retain generated packages, URLs with query data, bodies, or raw command output. CA failures identify only `failure_stage: "ca"`. The log never copies API keys, certificates, private keys, bundle contents, cookies, traffic bodies, or raw service logs.

Repository, dependency, and metadata acquisition must use the supplied verified bundle. A proxy trust failure must not be bypassed with `curl -k`, `--insecure`, or `GIT_SSL_NO_VERIFY=true`; artifacts acquired through such a channel have weak provenance and must be reacquired after trust is repaired. This does not prevent an explicitly scoped negative TLS test against a target with intentionally invalid TLS.

Host-side API calls use ZAP's explicit local API authority rather than proxy routing. During Brief, each traffic or final policy candidate is committed only after all current controls are accepted and attested; a failed installation cannot save that candidate or permit handoff. Upstream ZAP errors return bounded, sanitized `zap_*` fields. Cyberful response-validation failures instead return a `validation_code` and a shape-only projection containing field names and value kinds, never response values; they are not mislabeled as ZAP error codes. Both carry `retryable: false`, `user_action_required: false`, and `policy_stored: false` for the individual tool call. Brief records that technical blocker once and stops without asking the operator to repair an otherwise healthy runtime from inside the run.

The gateway also writes the first mandatory-upstream failure to one nonce-scoped, owner-private signal outside the workarea. The phase host consumes that bounded record before deliverable and handoff validation, classifies the phase as retryable `upstream/required_upstream_unavailable`, and removes the signal. A correct stop-without-handoff therefore cannot be misreported as `handoff_invalid`; the existing phase-recovery policy may start one fresh owner on the same provider route and rerun ZAP preflight.

Gateway startup, upstream connection, tool, and shutdown failures are retained locally in `raw/operations/runtime-diagnostics.jsonl`. Records preserve a sanitized host/port error class and repetition count but remove credentials, cookies, URL userinfo/query values, HTTP bodies, prompts, controls, and the full environment. The model does not receive these diagnostics automatically.

## History replay

`zap_http_request` treats an application response as a completed tool call for every HTTP status. Its local egress envelope records the effective host, method, path family, and response status, so expected denials remain evidence instead of MCP failures. ZAP API or transport failures remain tool errors.

`zap_history_replay` clones one selected history message inside ZAP and applies up to 32 bounded header, query, or JSON Pointer mutations before sending exactly one request. Scheme, authority, path, and method remain immutable; `Content-Length` is rebuilt and redirects default off. Captured cookies and authorization headers never return to the model. The result contains only message IDs, response metadata, sizes, and the non-secret mutation summary; call `zap_history_get` explicitly when complete bodies are required. This path supports freshness, nonce, replay, and KMS-style payload tests without standalone ZAP scripts.

## Incremental HTTP surface collector

The phase gateway owns a passive collector over the existing `zap_history_search` bridge operation. It requests metadata-only pages of at most 100 records without exposing those internal calls to the model. If a page exceeds the gateway response ceiling, the collector halves the page size and keeps the safe size for the rest of that synchronization. Synchronization occurs after every numbered target-profile agent-browser operation, after ZAP HTTP request, history replay, or generic API operations, and before an exhausted hypothesis synthesis, handoff, or gateway shutdown. The collector reads only traffic ZAP has already captured: it does not generate requests, mutate the session, run a scanner, or wait for the passive-scan queue.

For each message, the version-3 coverage ledger retains only the bounded ZAP ID, HTTP(S) origin, redacted route family, method, status, and whether any response was present. Query strings, headers, bodies, cookies, and payload values never enter this path. An exact or wildcard `authorized_http_hosts` match places the observation in `http_surface`; all other observed hosts become `passive_dependency` records that remain visible but cannot drive a handoff guard or research continuation. ZAP is therefore the canonical source for HTTP surface. Browser and ZAP egress inferred by the gateway are not duplicated, while direct cyberful-os observations and protocols absent from ZAP remain separate.

The next history offset is atomically persisted at `raw/operations/zap-history-coverage.cursor.json` only after coverage records are durable. Phase changes and phase recovery resume there. A missing or corrupt cursor restarts at zero, and duplicate crash replays are harmless because HTTP summaries reduce route metadata as sets. A collector failure writes its typed cause and cursor into degraded coverage diagnostics without turning an otherwise successful browser or ZAP action into a tool error. Causes distinguish response-size overflow, ZAP history storage exhaustion, malformed projections, ordinary tool failures, and transport failures; a changed cause replaces stale diagnostic detail. A transport failure from a ZAP instance required by policy additionally retains the ordinary required-upstream causal signal.

Persistent ZAP sessions use a 262,144 KiB HSQLDB row cache instead of the upstream 32,000 KiB template. The image patches the template used for new sessions, while the entrypoint updates the closed textual session script before reopening an existing session. This addresses the `Data cache size limit is reached` failure at its storage source; adaptive bridge paging remains a separate safeguard for bounded MCP responses.

This incremental map is independent from the post-phase passive-evidence checkpoint below. The map is immediate metadata used for research coverage and never waits for passive analysis; the checkpoint runs only after an accepted phase and may briefly wait for passive analysis to create immutable report evidence.

## Automatic passive evidence checkpoints

After every accepted Pentest and Bug Bounty phase, including an accepted budget-synthesized handoff and the terminal Report handoff, the host waits until that phase's Pi owner and private gateway have exited and then captures passive evidence before starting the successor. Failed attempts without an accepted handoff do not create a checkpoint; a successful recovery attempt records its own attempt number. Code Audit and Ask never invoke this path.

The checkpoint reads only the finalized `raw/policy/engagement.json`. An empty `authorized_http_hosts` list writes a `not_applicable` manifest without opening a ZAP bridge or issuing a ZAP call. Otherwise the host reads the ZAP site tree once, normalizes observed HTTP(S) origins, and retains only origins whose hostname matches an exact authorized host or a wildcard. `*.example.com` includes subdomains but not `example.com`; a port, path, query, or userinfo may distinguish an observed origin but cannot widen hostname authorization. If no authorized origin was observed, the host writes `no_observed_traffic` without reading or waiting for the passive queue and without generating a report. ZAP remains engagement-owned and always active for Pentest and Bug Bounty; the checkpoint adds no scanner work to SSH-only or native targets whose finalized HTTP host list is empty.

For applicable traffic, the host reads the passive queue and polls every 500 milliseconds for at most 10 seconds. It then asks `zap_generate_workarea_report` for `traditional-json` output in groups of at most 100 exact origins. The bridge validates each optional `sites` value as a normalized HTTP(S) origin and passes each group to the Reports API as a pipe-separated filter. Before publication, the host parses every generated report, rejects a batch if any reported site is outside the authorized host policy or the requested origin group, and removes site-bound ZAP insights outside that group while retaining site-independent diagnostics.

Validated bytes are published atomically as immutable content-addressed objects under `raw/zap/passive/objects/<sha256>.json`. The current version-1 phase manifest is `raw/zap/passive/<workflow>/<phase>.json`, and the append-only history is `raw/operations/zap-passive-evidence.jsonl`. A manifest records workflow, phase, attempt, timestamp, authorized hosts, included observed origins, initial and final queue depths, waited milliseconds, drain status, and each object's path, SHA-256, byte length, and covered sites. The phase runtime manifest exposes the state and manifest path, and the accepted summary passed to the successor includes the same host-owned reference.

`complete` means the queue drained and every batch was published. `partial` means the queue timed out or at least one batch failed while another was published. `failed` means ZAP or reporting was unavailable or no batch could be published. `partial` and `failed` add a warning but never change `PhaseResult.ok`, the handoff, or successor advancement; `not_applicable` and `no_observed_traffic` are silent. Pentest and Bug Bounty Report read the Verify checkpoint instead of generating a complete unfiltered session report. The checkpoint captured after Report is archival evidence. ZAP alerts are derived leads, not findings, and neither an alert nor an empty report is a vulnerability verdict.

## OAST adapter

Call `zap_oast` without an operation to read the capability contract derived from the installed add-on's live API catalog. Supported calls are exposed under the single `oast` component and successful calls return an explicit `completed` result with `data` or `empty` state.

The packaged add-on's HTTP API provides service discovery and configuration; it does not provide registration, payload generation, polling, or interaction history. Cyberful rejects guessed `interactsh`, `boast`, and `callback` subcomponents before transport. A justified callback test therefore uses a separate engagement-owned one-shot harness with a successful self-test, bounded polling, redacted evidence, and cleanup.

An individual HTTP outcome applies to the current request or scan and is not a phase-wide stop. A request or scan that returns `429` is not retried. Continue independent authorized work only while the target is stable; explicit mission stop conditions, scope uncertainty, systemic instability, unexpected private data, and unplanned side effects still stop target traffic.
